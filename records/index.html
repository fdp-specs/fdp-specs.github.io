Abstract

This document specifies FDP Records Management, an optional conformance class of the FAIR Data Point (FDP) specification suite. It defines how an FDP supports the creation, modification and deletion of metadata records through its HTTP interface, including server-side validation against the applicable metadata schemas.

1. Introduction

FDP Core specifies how metadata records are served; this module specifies how they are managed. A deployment implementing this module allows authorised clients to add, edit and delete metadata records through the same HTTP interface used for reading, following the resource semantics of the Linked Data Platform [LDP]: records are created by POSTing to their parent container, replaced with PUT, and removed with DELETE.

Terminology is defined in the umbrella document. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in [RFC2119].

This module specifies interface behaviour only. How an implementation stores records, manages users, or evaluates access policies is out of scope; what is normative is the observable HTTP behaviour, including the guarantee that write operations can be protected.

2. Conformance

This document defines the conformance class identified by:

https://specs.fairdatapoint.org/v2.0/conformance/records

A deployment conforms to FDP Records Management if and only if it conforms to FDP Core and satisfies all MUST-level requirements in this document.

REC-01

A deployment claiming this conformance class MUST also conform to the FDP Core conformance class of the same suite version.

3. Creating records

REC-02

Creation of a metadata record MUST be supported via an HTTP POST request on the IRI of the parent container (e.g. the catalog container of the FDP for a new catalog, or a catalog’s own container for a new record in that catalog), with the record’s RDF as the request body.

REC-03

For write request bodies, the deployment MUST accept at least RDF Turtle (text/turtle) and JSON-LD (application/ld+json), interpreting the Content-Type header; an unsupported Content-Type MUST be answered with status code 415.

REC-04

Before persisting, the deployment MUST validate the submitted record against the metadata schema applicable to the record’s type; if validation fails, the deployment MUST return status code 422 and MUST include the SHACL validation report [SHACL] in the response body, serialised in the negotiated RDF syntax (Turtle by default).

REC-05

On successful creation, the deployment MUST return status code 201 with a Location header carrying the IRI assigned to the new record; the assigned IRI MUST be dereferenceable per Core.

REC-06

On successful creation, the deployment MUST add the new record’s IRI to the parent container’s ldp:contains listing and, where applicable, add the corresponding domain-predicate triple (e.g. fdp-o:metadataCatalog) to the parent record.

Note: IRI assignment is the server’s responsibility; a client MAY propose an IRI (e.g. via the LDP Slug header), and the server MAY honour it, but the authoritative IRI is the one returned in Location.

4. Modifying records

REC-07

Modification of a metadata record MUST be supported via an HTTP PUT request on the record’s IRI, interpreted as a full replacement of the record’s content, subject to the same validation behaviour as REC-04; success MUST be answered with status code 200 or 204.

REC-08

A deployment MAY additionally support partial modification via HTTP PATCH; if PATCH is supported, the accepted patch format(s) MUST be advertised via the Accept-Patch response header.

REC-09

The deployment MUST maintain fdp-o:metadataIssued (set at creation, immutable thereafter) and fdp-o:metadataModified (updated at every successful modification) on every record managed through this interface; client-supplied values for these properties MUST be ignored or rejected.

REC-10

To prevent lost updates, the deployment SHOULD support conditional writes: honouring If-Match/If-Unmodified-Since on PUT, PATCH and DELETE, and answering 412 when the precondition fails.

Open question — which PATCH format(s) should be named? REC-08 deliberately leaves the patch format open. Candidates: SPARQL 1.1 Update (expressive, widely implemented in triple stores, but a full query language as a patch format has security and complexity implications), LD Patch (designed for exactly this use in the LDP family, but with limited implementation uptake), and RDF Patch / TriG-diff style formats (simple, but not standardised). Naming one format would improve interoperability of write clients; naming none keeps the barrier for implementers low since PUT full-replacement is always available. The community group should decide whether interoperable partial update is worth mandating a specific format in a future version.

5. Deleting records

REC-11

Deletion of a metadata record MUST be supported via an HTTP DELETE request on the record’s IRI; on success the deployment MUST return 200 or 204, MUST remove the record’s IRI from every container that listed it, and MUST remove the corresponding domain-predicate triples from the parent record(s).

REC-12

When a DELETE targets a record that leads to other records (a non-empty parent, e.g. a catalog with datasets), the deployment MUST either refuse the operation with status code 409 or delete the contained records recursively; whichever behaviour is implemented MUST be applied consistently and SHOULD be stated in the deployment’s service documentation. The deployment MUST NOT leave orphaned records that are no longer reachable from any catalog (which would violate Core requirement CORE-03).

REC-13

After successful deletion, a GET on the record’s IRI MUST return 404 or 410.

6. Access control at the interface

Metadata is generally openly readable, but it is expected that only a select group of agents may add, edit or delete records. How authentication and authorisation are implemented (accounts, tokens, federated identity, policy languages) is out of scope; what this module requires is that protection is possible and that its observable behaviour is uniform.

REC-14

The deployment MUST be able to require authentication for every operation defined in this module; when an unauthenticated request requires authentication, the deployment MUST return status code 401; when an authenticated agent lacks permission, the deployment MUST return status code 403.

REC-15

Authentication and authorisation requirements MUST NOT alter read behaviour required by Core for openly readable records; a deployment MAY additionally restrict reading of specific records or parts of records.

Open question — should interface-level access-control requirements move to Core? REC-14 and REC-15 live in this module because Core is read-only and public in the common case. However, deployments exist whose read side is partially restricted (e.g. sensitive-domain metadata behind authentication), and today Core says nothing about how such restrictions behave (401/403 semantics on GET, discoverability of restricted records in containers). Moving the requirements to Core would give restricted-read deployments a specified behaviour, at the cost of enlarging the mandatory class with requirements many public deployments never exercise; alternatively a separate small "Access Control" conformance class could be defined. The same question affects Schema Management and Bulk Ingestion, which currently reference the requirements defined here.

7. Requirements summary

FDP Records Management requirements
ID Level Summary
REC-01 MUST Core conformance is a prerequisite
REC-02 MUST Create via POST on the parent container
REC-03 MUST Turtle and JSON-LD accepted on write; 415 otherwise
REC-04 MUST SHACL validation before persisting; 422 + validation report on failure
REC-05 MUST 201 + Location with the assigned IRI
REC-06 MUST Containers and parent record updated on creation
REC-07 MUST Full replacement via PUT, validated
REC-08 MAY PATCH; formats advertised via Accept-Patch
REC-09 MUST Server-maintained metadataIssued/metadataModified
REC-10 SHOULD Conditional writes (If-Match), 412 on failure
REC-11 MUST DELETE removes record and all containment/domain triples
REC-12 MUST Non-empty parents: refuse (409) or cascade, consistently; no orphans
REC-13 MUST 404/410 after deletion
REC-14 MUST Write operations protectable; 401/403 semantics
REC-15 MUST Protection does not alter Core read behaviour for open records

Conformance

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
