Abstract

This document specifies FDP Bulk Ingestion, an optional conformance class of the FAIR Data Point (FDP) specification suite. It defines how a bundle of metadata records is added to an FDP in a single operation, including bundle representation, validation, transactionality and partial-failure reporting.

1. Introduction

Populating an FDP one record at a time through Records Management is impractical when migrating an existing repository, mirroring another catalogue, or publishing the output of a pipeline that produces many records at once. This module specifies bulk ingestion: adding a bundle of metadata records — possibly spanning multiple levels of the metadata structure, e.g. a catalog together with its datasets and their distributions — to an FDP in a single operation.

Terminology is defined in the umbrella document. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in [RFC2119].

2. Conformance

This document defines the conformance class identified by:

https://specs.fairdatapoint.org/v2.0/conformance/bulk

A deployment conforms to FDP Bulk Ingestion if and only if it conforms to FDP Core and FDP Records Management and satisfies all MUST-level requirements in this document.

BLK-01

A deployment claiming this conformance class MUST also conform to the FDP Core and FDP Records Management conformance classes of the same suite version.

Note: Records Management is a prerequisite because bulk ingestion is semantically a batch of record creations: validation, IRI assignment, container updates and access control are all inherited from that module and only their batch behaviour is specified here.

3. The bundle

BLK-02

Bulk ingestion MUST be supported via an HTTP POST on the IRI of the container under which the bundle’s top-level records are to be created, with Content-Type: application/trig and a TriG [TRIG] document as the request body; receiving a TriG body is what distinguishes a bulk operation from a single-record creation on the same container.

BLK-03

In the bundle, each named graph MUST contain exactly one metadata record; the graph names act as temporary, bundle-local identifiers.

BLK-04

Records within a bundle MAY reference each other using their bundle-local graph names; the deployment MUST resolve such references to the IRIs it assigns on ingestion, so that hierarchical structures (e.g. catalog → datasets → distributions) can be created in one operation with correct parent–child relations and navigation information.

BLK-05

On successful ingestion the deployment MUST return a response listing, for every record in the bundle, the bundle-local graph name and the assigned IRI; each ingested record MUST afterwards be individually retrievable and navigable exactly as if it had been created through Records Management.

4. Validation and transactionality

BLK-06

Every record in the bundle MUST be validated against its applicable metadata schema, with the same semantics as single-record creation (REC-04 in Records Management).

BLK-07

By default, bulk ingestion MUST be atomic: if any record in the bundle fails validation, or if ingestion fails for any other reason, no record from the bundle is persisted, and the deployment MUST return status code 422 with a report that identifies, per failing record (by bundle-local graph name), the SHACL validation report or error.

BLK-08

A deployment MAY offer a non-atomic mode, in which valid records are persisted and invalid ones are reported; this mode MUST only be applied when the client explicitly requests it (e.g. via Prefer: handling=lenient), and the response MUST report the outcome for every record in the bundle.

5. Large bundles

BLK-09

A deployment MAY process bundles asynchronously: it then MUST return status code 202 with a Location header pointing to a status resource, and a GET on the status resource MUST report the ingestion’s state (in progress, succeeded, failed) and, on completion, the result described in BLK-05 or the failure report of BLK-07.

BLK-10

A deployment MAY enforce a maximum bundle size; a bundle exceeding it MUST be answered with status code 413, and the limit SHOULD be stated in the deployment’s service documentation.

BLK-11

Access control for bulk ingestion MUST follow the same interface behaviour as Records Management (REC-14, REC-15).

Open question — bundle representation. This draft uses TriG on the target container (BLK-02, BLK-03) because it needs no new endpoint, no packaging tooling, and reuses the media type to signal bulk semantics; one named graph per record also gives the per-record validation reporting of BLK-07 a natural addressing unit. Alternatives the community group should weigh: (a) a single flat RDF graph (e.g. one large Turtle document) — simpler to produce, but record boundaries must then be inferred from typing and containment, which makes per-record reporting and bundle-local referencing (BLK-04) ambiguous; (b) a packaged bundle format such as an RO-Crate-like archive — attractive when records come with attachments or when provenance of the bundle itself must travel with it, but it introduces a packaging dependency that plain metadata migration does not need; (c) a dedicated bulk endpoint instead of overloading the container POST — cleaner separation and easier to document/advertise, but it adds surface that must be discoverable from the FDP’s own metadata. A related question is whether the asynchronous mode of BLK-09 should be mandatory above a stated bundle size, so that clients can rely on it for large migrations.

6. Requirements summary

FDP Bulk Ingestion requirements
ID Level Summary
BLK-01 MUST Core and Records Management are prerequisites
BLK-02 MUST Bulk via POST of TriG on the target container
BLK-03 MUST One named graph per record
BLK-04 MUST Bundle-local cross-references resolved to assigned IRIs
BLK-05 MUST Response maps graph names to assigned IRIs; records fully navigable
BLK-06 MUST Per-record SHACL validation as in Records Management
BLK-07 MUST Atomic by default; 422 with per-record failure report
BLK-08 MAY Lenient mode on explicit request, with full per-record outcome
BLK-09 MAY Asynchronous processing: 202 + status resource
BLK-10 MAY Size limits; 413 when exceeded
BLK-11 MUST Access control per Records Management interface behaviour

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
