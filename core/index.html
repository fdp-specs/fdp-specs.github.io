Abstract

This document specifies FDP Core, the mandatory conformance class of the FAIR Data Point (FDP) specification suite. FDP Core defines the read-side behaviour of a FAIR Data Point: how metadata records are served over HTTP, how clients navigate the metadata structure, and how metadata schemas are exposed. Implementing FDP Core is the necessary and sufficient condition for a system to claim that it behaves as a FAIR Data Point.

1. Introduction

This document defines FDP Core, the mandatory module of the FAIR Data Point specification suite. It specifies the externally observable, read-side behaviour of a FAIR Data Point: the HTTP interface through which metadata records are served, the representations in which they are served, the navigation information that lets clients traverse the metadata structure, and the exposure of metadata schemas.

Terminology used in this document (metadata record, metadata schema, profile, container, conformance class) is defined in the umbrella document. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in [RFC2119].

Note: This document specifies behaviour, not architecture. How an implementation stores its metadata (native triple store, on-the-fly conversion from another representation, static files) is out of scope; any implementation whose observable behaviour satisfies the requirements below conforms.

2. Conformance

This document defines the conformance class identified by:

https://specs.fairdatapoint.org/v2.0/conformance/core

A deployment conforms to FDP Core if and only if it satisfies all MUST-level requirements in this document (§ 8 Requirements summary lists them). Conformance to FDP Core is the necessary and sufficient condition for claiming that a system behaves as a FAIR Data Point.

3. The root metadata record

A client that knows nothing about a deployment except its root URL must be able to bootstrap all further interaction from that URL alone. The FDP therefore provides metadata about itself as the first metadata record: the record of the FDP as a metadata service. In the FDP ontology, the FAIR Data Point is represented by the class fdp-o:FAIRDataPoint, a subclass of fdp-o:MetadataService, which in turn is a subclass of dcat:DataService.

CORE-01

The root URL of the deployment MUST serve the metadata record of the FDP itself, typed fdp-o:FAIRDataPoint.

CORE-02

The FDP’s own metadata record MUST declare, via dct:conformsTo, the URI of every conformance class of this suite that the deployment implements, including at least the FDP Core conformance class URI.

CORE-02 is the machine-checkable capability and version declaration described in the umbrella document: because the conformance class URIs are versioned, a single dct:conformsTo statement declares both a capability and the specification version that defines it. The FAIR Data Point metadata schema (§ 7.1 FAIR Data Point metadata schema) enforces this declaration.

4. Metadata model

The FDP uses the W3C’s Data Catalog Vocabulary (DCAT) version 2 [VOCAB-DCAT-2] as the basis for its metadata content. Figure 1 depicts the FDP extensions to the DCAT model.

A DCAT Resource represents entities that can be described by a metadata record. Since Resource is defined as an abstract class, it is not intended to be used directly; one of its subclasses, such as Dataset or Data Service, is used instead. Dataset represents a collection of data while Data Service represents a service, accessible through an interface (API), that serves datasets. Catalog, a subclass of Dataset, represents aggregations of metadata records about digital objects; for instance, a Catalog may contain references to the metadata records of Datasets.

The FDP extends the DCAT model by adding the concept of a FAIRDataPoint as a specific type of data service that serves metadata catalogs and metadata records. The DCAT extensions and other FDP-specific concepts and relations are defined in the FDP ontology (namespace prefix fdp-o). The relation between the MetadataService and dcat:Catalog is represented by the predicate fdp-o:metadataCatalog, defined as a sub-property of dcat:Relationship having fdp-o:MetadataService as its domain and dcat:Catalog as its range.

CORE-03

Every metadata record served by the deployment, other than the FDP’s own record, MUST be reachable from at least one dcat:Catalog record.

Since only the FDP’s own record and Catalog records are mandatory, the metadata structure below the catalogs varies from deployment to deployment. The most common structure is FAIR Data Point → Catalog → Dataset → Distribution, but another deployment could use, e.g., FAIR Data Point → Catalog → Semantic Artefact. This flexibility is exactly why the navigation information of § 6 Navigation information is mandatory.

5. HTTP interface

The interface of the FDP follows the REST HATEOAS (Hypermedia as the Engine of Application State) principle: each response carries the information a client needs to discover the available resources. A client only needs the root URL (CORE-01); everything else is discoverable by following the navigation information in the returned metadata.

5.1. Retrieval

CORE-04

Every metadata record, every container, and every metadata schema MUST be retrievable via an HTTP(S) GET request on its IRI, returning status code 200 together with the resource’s representation.

CORE-05

Every resource that supports GET MUST also support HEAD, returning the same headers as the corresponding GET without a body.

CORE-06

A GET request on an IRI within the deployment’s namespace that does not identify an existing resource MUST return status code 404; a deployment MAY return 410 for resources known to have been deleted.

5.2. Representations and content negotiation

CORE-07

Metadata content MUST be available at least in the RDF Turtle (text/turtle) and JSON-LD (application/ld+json) syntaxes, selectable via the HTTP Accept header.

CORE-08

When a request carries no Accept header, an Accept header of /, or an Accept header that does not restrict the response to a specific supported type, the response MUST be RDF Turtle.

CORE-09

When a request’s Accept header admits none of the supported media types, the deployment MUST return status code 406; the response SHOULD list the supported media types.

Other formats — XML, JSON, other RDF syntaxes, or HTML for human consumption — MAY additionally be offered through content negotiation.

5.3. Caching and change information

Accurate change information matters beyond caching: harvesters (such as a FAIR Discovery service) rely on it to keep aggregated copies fresh without re-fetching entire trees, and to report a record’s real modification time rather than its harvest time.

CORE-10

Responses serving metadata records SHOULD carry an ETag and/or Last-Modified header, and the deployment SHOULD support the corresponding conditional requests (If-None-Match, If-Modified-Since) returning 304 when the resource is unchanged.

Note: The mandatory schema elements fdp-o:metadataIssued and fdp-o:metadataModified (§ 7.1 FAIR Data Point metadata schema) provide the same information inside the metadata record itself.

6. Navigation information

Since each FDP deployment may have a different metadata structure (§ 4 Metadata model), a client would not know how to navigate the metadata content unless it followed every IRI in every record, which does not scale. Therefore, the FDP describes its own navigation structure using the Linked Data Platform [LDP] containment vocabulary.

CORE-11

Every metadata record that leads to other metadata records MUST be accompanied by navigation information in the form of an LDP container, and the record MUST be retrievable together with, or linked to, that container’s triples.

CORE-12

Each container MUST list the IRI of every child metadata record as an object of ldp:contains.

CORE-13

When the parent record relates to its children through a domain predicate (e.g. fdp-o:metadataCatalog), the container SHOULD be an ldp:DirectContainer declaring that predicate via ldp:hasMemberRelation and the parent record via ldp:membershipResource.

Note: Version 1.2 of this specification was internally inconsistent about navigation: its metadata chapter required "ldp:contains or ldp:hasMemberRelation", while its compliance chapter required ldp:hasMemberRelation alone. Version 2.0 resolves this deliberately in favour of ldp:contains as the mandatory traversal predicate (CORE-12), because containment is what generic clients and harvesters walk, while the membership declaration (CORE-13) is a recommendation that adds the domain semantics when they exist.

The following RDF Turtle code shows an example of a FAIR Data Point metadata record with navigation information.

In this record, the FDP has the relation fdp-o:metadataCatalog with its catalogs — the parent–child relation a client follows to navigate the structure. The container <https://purl.org/fairdatapoint/app/catalog/> makes the structure explicit: it declares the FDP record as its ldp:membershipResource, fdp-o:metadataCatalog as its ldp:hasMemberRelation, and lists the member catalogs via ldp:contains.

7. Metadata schemas and profiles

The FAIR Data Point supports deployment-defined metadata schemas, following the acknowledgment that every application scenario may require different sets of properties to properly describe a given digital object.

CORE-14

Every metadata schema used by the deployment MUST be expressed in SHACL [SHACL].

CORE-15

Every metadata schema MUST declare as its target class dcat:Resource or a subclass of dcat:Resource.

CORE-16

Each metadata record SHOULD reference its profile via dct:conformsTo.

CORE-17

A profile IRI referenced by a metadata record MUST be retrievable (§ 5.1 Retrieval) and MUST resolve to the record’s metadata schema expressed in SHACL.

**Open question — should CORE-16 be promoted from SHOULD to MUST?** In version 1.x the profile reference was a SHOULD. Arguments for MUST: without the profile link, a client or harvester cannot validate a record or discover its schema mechanically, which undermines the predictability goal of the suite; and the two mandatory record types (the FDP’s own record and catalogs) already carry a mandatory dct:conformsTo in their schemas, so the gap only exists for deployment-defined types. Arguments for keeping SHOULD: deployments that expose legacy or third-party metadata may be unable to attach profiles to records they do not control, and a MUST would exclude them from Core conformance entirely rather than degrading gracefully. A possible middle ground is MUST for records created through the Records Management interface and SHOULD otherwise.

Since only the FDP’s own record and Catalog records are mandatory, the metadata structure below the catalogs varies per deployment. As the FDP is most commonly used to provide metadata of datasets, deployments typically also define Dataset and Distribution schemas following the DCAT model; deployments are free to replace these with custom schemas, as long as CORE-15 is satisfied. If other types of digital objects are used, the catalog metadata must contain the navigation information from the catalog to those records, per § 6 Navigation information.

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.

**Open question — should CORE-16 be promoted from SHOULD to MUST?** In version 1.x the profile reference was a SHOULD. Arguments for MUST: without the profile link, a client or harvester cannot validate a record or discover its schema mechanically, which undermines the predictability goal of the suite; and the two mandatory record types (the FDP’s own record and catalogs) already carry a mandatory dct:conformsTo in their schemas, so the gap only exists for deployment-defined types. Arguments for keeping SHOULD: deployments that expose legacy or third-party metadata may be unable to attach profiles to records they do not control, and a MUST would exclude them from Core conformance entirely rather than degrading gracefully. A possible middle ground is MUST for records created through the Records Management interface and SHOULD otherwise. ↵
